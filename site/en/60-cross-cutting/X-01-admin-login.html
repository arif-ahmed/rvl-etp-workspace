X-01 Admin login (phone OTP + password)

Bangla name: অ্যাডমিন লগইন (ফোন OTP + পাসওয়ার্ড)

← 60 · Cross-cutting · Contents · Open queries

1. Name and purpose

Admin login. Lets BCB and BS23 staff (roles admin, event_manager, ticket_manager, ticket_operator, customer_support) sign in to the admin portal. The screen asks for three things in turn: the 10-digit phone number, a 6-digit SMS code, and the Cognito password. A successful login gives the browser Cognito tokens from the Admin user pool, which every admin API call then carries.

2. Trigger and actor

Item Value
Actor Staff member with an account in the Admin Cognito pool (created by X-05)
Client and screen Admin portal, route /auth/login (LoginComponent)
Cognito pool Admin (environment.aws.userPoolId / userPoolWebClientId)
Role / program scope None needed to log in; the role decides the landing page afterwards

3. Business flow

  1. The staff member types the phone number without +880.
  2. The portal asks the "Serverless" API to send a 6-digit code by SMS. If the number is unknown, the message is "User not found."
  3. The staff member types the code; the portal asks the Serverless API to verify it. A resend is allowed after 2 minutes.
  4. After a valid code, the password field appears. The portal signs in to Cognito with +880<phone> and the password.
  5. The portal reads the role (custom:role) and opens the landing page: /program-management for admin, event_manager (alone or with ticket_manager); /home for the others.
  6. For the roles admin, ticket_manager and ticket_operator the portal also asks Ticketing for CloudFront signed cookies, so reserved-ticket files can be downloaded later (A-12).

4. Technical flow

# From → To Hop What happens
1 Admin portal → Serverless API POST {serverless.baseUrl}/admin/login-2fa-send-otp [HTTP, static key] Body { otp_type: "sms", destination: "+880…" }, header Authorization: <environment.serverless.authorization>. Success when status_message == "otp_generated_and_enqueued_successfully"
2 Admin portal → Serverless API POST …/admin/login-2fa-verify-otp [HTTP, static key] Body adds otp. Success when status_message == "sms_otp_verified_successfully"; invalid_otp otherwise
3 Admin portal → Cognito (Admin pool) Amplify Auth.signIn(phone, password) SRP sign-in (Amplify's default flow; locally the setup script enables ALLOW_USER_SRP_AUTH). Returns tokens, or a challenge
3a challenge NEW_PASSWORD_REQUIRED The portal answers with Auth.completeNewPassword(response, <same password>), so the temporary password becomes permanent
3b challenge SMS_MFA Returned to the caller as a value, not handled (see notes)
4 Admin portal → Cognito Auth.currentSession(), Auth.currentUserInfo() Access token cached for 55 minutes; user attributes (including custom:role) cached for 55 minutes
5 Admin portal → Ticketing GET /ticketing/api/v1/booking-order-ticket/signed-cookie [HTTP + user token] Only for roles admin, ticket_manager, ticket_operator; the response's CloudFront-* cookies are written with document.cookie

No backend service is involved in steps 1–4. The services see the user only on the next API call, when they validate the Admin-pool access token (X-14).

7. Data and side effects

  • Nothing is written by the GoBCB backend during login.
  • The Serverless API sends an SMS (outside the repos).
  • The browser stores Amplify's tokens, sessionStorage.lastKnownUserRole (used by role-change detection, X-17), and for three roles the CloudFront cookies.

9. Handover notes

  1. The SMS code is checked only by the browser. Step 3 sends just phone and password to Cognito; nothing from the OTP step reaches Cognito or the services. Anyone who knows a staff password can get Admin-pool tokens by calling Cognito directly (as the Postman request "Login as admin" does locally). Whether the Admin pool itself enforces MFA is not visible in the repos [UNCONFIRMED: Q-03].
  2. The Serverless key is in the browser bundle. environment.serverless.authorization is part of the generated environment.ts, so every visitor of the admin portal can read it.
  3. NEW_PASSWORD_REQUIRED silently re-uses the typed password. Accounts created by the Admin service already get a permanent password (X-05), so this branch matters only for accounts created another way.
  4. SMS_MFA is not handled. signIn resolves with { challengeName: 'SMS_MFA', … }; onLogin treats that as success and then fails to read the role because the user is not signed in. confirmMFA(user, code) exists but no screen calls it.
  5. Signed-cookie roles use an exact match. allowedRoles.includes(role) compares the whole custom:role string, so a user whose attribute holds two roles (for example event_manager,ticket_manager) gets no cookie at login. The top bar has a "refresh cookie" action (RefreshCookie() in app.topbar.component.ts).
  6. Role cache. The role shown and used by the menu is cached for 55 minutes in the browser; a role change by an admin takes up to that long to be noticed (X-17). The backend has its own cache (X-15).
