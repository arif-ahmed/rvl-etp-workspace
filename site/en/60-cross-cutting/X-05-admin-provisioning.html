X-05 Staff account provisioning

Bangla name: স্টাফ অ্যাকাউন্ট তৈরি

← 60 · Cross-cutting · Contents · Open queries

1. Name and purpose

Staff account provisioning. Staff never sign up themselves. An administrator creates every admin, ticket-checker and agent account from the admin portal; the Admin service then creates the user directly in the matching Cognito pool, sets a generated permanent password, and sends the username and password to the phone by SMS. The same service disables, enables, deletes and resets those accounts. This file describes the shared mechanics; the screens are in A-25 (admins), A-17 (checkers) and A-26 (agents).

2. Trigger and actor

Item Value
Actor Admin-portal user in the global menu (program 0). Admin accounts: role admin. Checker accounts: admin, event_manager, ticket_manager, ticket_operator (controller roles). Agent accounts: no server-side restriction (see notes)
Client and screen Admin portal → Users → "Regular Admins" (/users), "Ticket Checkers" (/ticket-checker), "Seller Agents" (/agent-user); menu shown for admin only (X-17)
Cognito pools written Admin, TicketChecker, Agent

3. Business flow

  1. The administrator fills in name, phone (the form adds +880), email and, for admins, one or more roles and the programs the user may work on.
  2. The account is created and the new user receives an SMS: "Your account has been created successfully. Your user name is and password is ".
  3. Later the administrator can edit name/role/programs, disable or enable the account, delete it, or "Set Password", which generates a new password and sends it by SMS.
  4. Disabling an account (and resetting its password) signs the user out on every device.

4. Technical flow

# From → To Hop What happens
1 Admin portal → Admin POST /admin/api/v1/admin-users (or /ticket-checker, /agent-users) [HTTP + user token] Body with name, phone, email, role(s), program ids
2 Admin service → Cognito AWS SDK, static keys AWS:AccessKey / AWS:SecretAccessKey Admin users: ListUsers(email = …) to refuse a duplicate email; then AdminCreateUser(Username = phone, attributes) with a temporary password, then AdminSetUserPassword(Permanent = true) with the same password
3 Admin service → Notification service POST /notification/send-message [HTTP, static key] SMS with username and password
4 Admin service → database — Activity log AdminUser / Created (admin accounts) (X-24)
U Update AdminUpdateUserAttributes name, custom:role, custom:program_ids (empty string when no programs), email_verified, phone_number_verified; the cached attributes user_{id} are removed
D Disable / enable AdminDisableUser / AdminEnableUser + AdminUserGlobalSignOut An admin cannot disable or delete itself (ArgumentNullException("Invalid permission") → 400)
P Set password AdminUserGlobalSignOut, AdminSetUserPassword(generated, Permanent), SMS with the new password Admins: body { userId }; checkers and agents: query ?userId=
X Delete AdminDeleteUser, cache entry removed

Attributes written per pool

Pool Username Attributes
Admin phone phone_number, name, email, custom:role (comma-separated roles), custom:program_ids (comma-separated ids, optional), email_verified=true, phone_number_verified=true
TicketChecker phone phone_number, name, email = <phone without +>@gobcbticket.com, custom:role = "TicketChecker"
Agent phone phone_number, name, custom:branch_location, custom:company_name, custom:company_branch, phone_number_verified=true, optional custom:email

Generated passwords: 8 characters with at least one upper case letter, lower case letter, digit and one of !@#$, built with System.Random (AdminUserProvider.GeneratePassword).

AdminUserResponse (ETP.Admin.Domain/Models/Users/Admin/AdminUserResponse.cs) is mapped with Mapster from the provider's AWSUserResponse (AdminUserProvider.cs:92-102). The provider's property is spelled IsPhoneNUmberVerified; no Mapster configuration exists in the repo, so with Mapster's default exact name matching it does not map to IsPhoneNumberVerified, which stays false (confirm with the Postman create request); currentStatus is not set on create. The Admin service does not omit nulls.

7. Data and side effects

  • Cognito user created, updated, disabled, enabled or deleted in the pool of the account type.
  • SMS with the username and password (create) or the new password (set password).
  • Global sign-out of the target user on disable, enable and set password.
  • Activity log rows for admin accounts (Created, Updated, Deleted, Disabled, Enabled, PasswordReset).
  • Cache key user_{userId} removed on update and delete, so the role change is seen by the next request on that service instance.

9. Handover notes

  1. Agent accounts can be managed without a token. AgentController has no [Authorize] and BaseController has its [Authorize] commented out, so /admin/api/v1/agent-users/* (create, set password, delete, …) is anonymous in the code. Whether the gateway blocks it is unknown [UNCONFIRMED: Q-04]. See X-18.
  2. Passwords are generated with System.Random and sent in clear text by SMS. The password is set as permanent, so Cognito never asks the user to change it at first login.
  3. Email uniqueness is checked only for admin accounts; the Cognito username is the phone number, so a phone can exist once per pool.
  4. Role and program changes are not instant everywhere. The Admin service clears user_{id} from its cache on update, but the UserIssue service has its own copy of the attribute cache (X-15), and the admin portal caches the role for 55 minutes (X-17). An already-issued access token stays valid until it expires.
  5. Checker custom:role is TicketChecker, which is not one of the role constants; the checker's role claim (ticket-checker) comes from the token scheme, not from this attribute (X-14).
  6. SMS failure leaves a half-done operation. The Cognito user and password are created before the SMS is sent; if the Notification service fails, the API returns 400 although the account exists.
